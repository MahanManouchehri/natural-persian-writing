# راهنمای کاربردی نگارش طبیعی فارسی

این راهنما برای تولید و بازنویسی متن فارسیِ طبیعی، دقیق و متناسب با موقعیت است.

## اصل محوری

معنا، دقت فنی، قصد نویسنده، اصطلاحات و سطح رسمی‌بودن متن را حفظ کنید؛ ساختار نامأنوس جملهٔ انگلیسی را حفظ نکنید.

## مستندات فنی و API

لحن باید حرفه‌ای، فنی، خنثی، مستقیم و قابل مرور سریع باشد. رفتار قابل مشاهدهٔ endpoint را توضیح دهید و جزئیات پیاده‌سازی را فقط زمانی بیاورید که برای مصرف‌کنندهٔ API مهم است.

- به‌جای `Notificationهای private کاربر جاری را صفحه‌بندی‌شده می‌خواند.` بنویسید: `Notificationهای خصوصی کاربر فعلی را به‌صورت صفحه‌بندی‌شده برمی‌گرداند.`
- به‌جای `Departmentهای active قابل انتخاب را برمی‌گرداند.` بنویسید: `لیست Departmentهای فعال و قابل انتخاب را برمی‌گرداند.`
- برای Mark-as-Read بنویسید: `Notification موردنظر را برای کاربر فعلی به حالت خوانده‌شده درمی‌آورد.`
- ورودی، خروجی و خطا را مستقیم توضیح دهید؛ مانند: `اگر داده‌های ورودی معتبر نباشند، پاسخ 422 برمی‌گردد.`

## مجوز و امنیت

قاعدهٔ دسترسی و نتیجهٔ نقض آن را با یک جملهٔ طبیعی و دقیق توضیح دهید: `فقط مالک Notification می‌تواند این عملیات را انجام دهد. تلاش برای دسترسی به Notification کاربر دیگر با پاسخ 403 Forbidden رد می‌شود.`

IDOR یک دستهٔ آسیب‌پذیری است و با status code «برابر» نیست. بررسی مالکیت، مجوزها، نقش‌ها، محدودهٔ دید منابع و محدودیت تغییر وضعیت را در ساده‌سازی حذف نکنید.

## فارسی رسمی و حرفه‌ای

رسمی‌بودن را با عبارت‌های اداری و فعل‌های سنگین اشتباه نگیرید.

- `کاربر باید شناسه را ارسال کند.`
- `اگر Conversation موردنظر پیدا نشود، پاسخ 404 برمی‌گردد.`
- `این عملیات گفت‌وگو را از پشتیبان فعلی آزاد می‌کند.`

## رابط کاربری و پیام خطا

متن UI باید کوتاه باشد و قدم بعدی را روشن کند.

- `عملیات انجام نشد.`
- `فایل آپلود نشد. دوباره امتحان کنید.`
- `شماره موبایل معتبر نیست.`

## پیام پشتیبانی

محترمانه، روشن و صمیمی باشید، بدون لحن اداری: `لطفاً یک تصویر از خطایی که می‌بینید ارسال کنید.`

## فارسی محاوره‌ای

در گفت‌وگوی واقعاً غیررسمی می‌توان از صورت‌هایی مانند «می‌تونی»، «می‌خوای» و «اگه» استفاده کرد. این املا را خودکار وارد مستندات فنی، تجاری، رسمی یا حقوقی نکنید.

## متن حقوقی، قراردادی و سیاستی

دقت بر ساده‌سازی اولویت دارد. تعهد، ممنوعیت، استثنا، دامنه، مسئولیت، اصطلاح تعریف‌شده و تضمین را آزادانه بازنویسی نکنید. فقط وقتی جمله را ساده کنید که اثر حقوقی آن تغییر نکند.

## کنترل کیفیت نهایی

1. آیا متن در اولین خواندن روشن است؟
2. آیا اصطلاحات پروژه و شناسه‌های کد دست‌نخورده مانده‌اند؟
3. آیا ساده‌سازی، قاعدهٔ فنی یا امنیتی را ضعیف نکرده است؟
4. آیا واژهٔ انگلیسی باقی‌مانده واقعاً مفید یا بخشی از قرارداد پروژه است؟
5. آیا متن بیش از حد محاوره‌ای یا بی‌دلیل اداری نشده است؟
